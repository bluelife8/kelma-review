# Test strategy

## Required local verification

```bash
./gradlew :shared:jvmTest
./gradlew :shared:iosSimulatorArm64Test
./gradlew :shared:verifySqlDelightMigration
./gradlew :shared:testAndroidHostTest
./gradlew :shared:connectedAndroidDeviceTest # with an emulator/device connected
./gradlew :desktopApp:compileKotlin :androidApp:assembleDebug
```

`./scripts/run-android-emulator.sh [AVD name]` builds the debug APK, reuses or boots the requested AVD, waits for `sys.boot_completed`, installs without clearing app data, and launches `MainActivity`. Set `ANDROID_EMULATOR_HEADLESS=1` for CI-style operation or `ANDROID_EMULATOR_BUILD_ONLY=1` to stop after assembly.

The JVM suite is the fastest application gate. The separate `kelma-fsrs-v6` build runs all 705 Python-oracle cases on JVM, Android host, Linux Native, macOS Native, and iOS Simulator Native; application common tests then verify the persistence and queue adapter on JVM and iOS.

`./scripts/run-ios-simulator.sh` builds the app with Xcode's ad-hoc **Sign to Run Locally** identity and verifies both the signature and simulated application-identifier entitlement before installation. Do not disable simulator code signing: an unsigned app can launch normally but every Security.framework Keychain request fails with `errSecMissingEntitlement` (`-34018`).

## FSRS validation

New/default scheduling is pinned to **FSRS-6** through the independent MIT `kelma-fsrs-v6` library, with fuzzing disabled, desired retention `0.9`, maximum interval `36500`, and 21 standard parameters. Customized 19-parameter FSRS-5 profiles remain labeled legacy and continue using the preserved compatibility engine.

Validation has these layers:

1. **Primary Python parity** — the standalone library runs 705 trajectories generated by `py-fsrs==6.3.1`, including every rating, learning/relearning, completed-day boundaries, ties-to-even rounding, custom profiles, duplicate/out-of-order reviews, and interval caps. The exact same fixture validates KelmaSync Go scheduling.
2. **Legacy profile parity** — `FsrsReferenceParityTest` keeps 48 `ts-fsrs` FSRS-5 cases plus 47 trajectory steps so customized 19-parameter profiles remain functional without being relabeled.
3. **Cross-platform behavioral and invariant tests** — `FsrsSchedulerCommonTest` checks transition ordering, overdue behavior, rejection of imported scheduling memory, same-day behavior, timestamp saturation, and a deterministic 2,000-review stress sequence on JVM and iOS. `ReviewQueueOrderingTest` independently verifies gather-before-sort admission, stable daily randomization, durable same-day new/review/interday sibling burying, daily-limit refill after burying, all queue-mixing positions, intraday/interday placement, and due/deck/interval/difficulty/retrievability/overdueness/added review orders without changing scheduler state.
4. **Persistence tests** — `PersistentCollectionStoreTest` verifies atomic review writes, restart restoration, sync preservation, account isolation, Undo, vault-backed token-preserving account switching, explicit credential removal, database migrations, persistent empty/nested deck creation, hierarchy rename/delete with card and review cleanup, downloaded-deck safety, duplicate and account-boundary handling, transactional note-add rollback, and reversed note types. `LocalAccountRegistryTest` verifies stable account-to-database mappings and legacy-database registration; `LocalAccountCollectionIsolationTest` proves account switching retains the vault token, explicit credential removal preserves content, and two account databases retain disjoint collections. `SignInScreenUiTest` opens a retained account directly without submitting a password, and `SyncWorkflowTest` verifies authenticated account initialization emits live preflight-through-completion progress. `DeckPresetPersistenceTest` covers shared edits, assignment, restart, deck/preset renaming, deletion without behavior changes, uniqueness, and account clearing.

### Updating FSRS

An FSRS version or parameter change must be deliberate:

1. Pin a permissively licensed reference release and verify its package integrity and algorithm version.
2. Generate a new fixture under a new filename; do not silently replace the old algorithm's vectors.
3. Run old and new fixtures and document every intentional scheduling difference.
4. Add a database migration if persisted scheduler state changes shape or meaning.
5. Run JVM, iOS, migration, desktop, and Android verification before merging.
6. Retain the previous fixture until existing collections have a documented migration/rescheduling policy.

Never weaken tolerances or edit expected values merely to make a failing implementation pass. A mismatch must first be classified as an implementation defect, an intentional queue-policy difference, or a reference-version change.

## Real collection FSRS acceptance

Run the opt-in read-only acceptance against an Anki collection:

```bash
./scripts/run-real-collection-fsrs-acceptance.sh \
  "/path/to/Anki2/Profile/collection.anki2"
```

The path defaults to the local macOS `User 1` collection. The test opens the
source with SQLite `mode=ro` and `query_only`, reads only card IDs, note IDs,
card ordinals, review IDs, ratings, and review kinds, and verifies that its size
and modification time do not change. It never selects note fields, tags, deck
names, media, credentials, or source scheduling projections.

Qualifying ratings are replayed directly through `kelma-fsrs-v6`, then inserted
in reverse order into an isolated temporary Kelma SQLDelight database. The
client rebuilds every projection, compares it field-for-field with the direct
result, closes and reopens the database, rebuilds again, and checks restart
determinism.

The Kotlin test also emits a temporary schedule-only NDJSON fixture. The pinned
`linux/amd64` `py-fsrs==6.3.1` Docker oracle and KelmaSync's internal Go
scheduler independently replay every card and compare final state, step,
timestamps, stability, difficulty, interval, repetitions, and lapses with the
Kotlin projection. Float comparisons use the canonical `1e-12` tolerance; all
other fields are exact. The fixture and temporary database are deleted. Reports
contain only aggregate counts, timings, and a metadata-only SHA-256 fingerprint.

This test is compiled during normal JVM and Go verification but reads no
collection unless the wrapper explicitly supplies its temporary inputs. The
wrapper expects `kelma_sync_2` beside this repository; set `KELMA_SYNC_REPO` to
override that location. It forces both selected tests to rerun.

## Private real-history optimizer acceptance

Run the separate optimizer comparison with:

```bash
./scripts/run-real-collection-optimizer-acceptance.sh \
  "/path/to/Anki2/Profile/collection.anki2"
```

The optimizer test has the same read-only source guarantees. It selects active
card identity plus review timestamp, rating, kind, and answer duration; no card
or note content is read. Kotlin formats and optimizes the history twice to prove
repeatability, then repeats it through a temporary migration-13 application
database and verifies candidate restart without changing the active profile. A
temporary content-free TSV is then optimized independently by the pinned `fsrs-optimizer==6.5.0` Linux container. Dataset hashes, eligibility, rounded optimized parameters, split counts, and
six-decimal loss metrics must match exactly. Initial values must be within
`1e-4`, accounting for SciPy scalar-minimizer stopping behavior; the maximum
observed difference is reported.
The TSV and machine comparison result are removed when the wrapper exits.
Reports contain only aggregate counts, candidate parameters, losses, timings,
and a metadata fingerprint.

`KELMA_OPTIMIZER_TIMEZONE` and `KELMA_OPTIMIZER_DAY_START_HOUR` select the frozen
study-day policy; defaults are `America/New_York` and `4`. Set
`KELMA_FSRS_REPO` if `kelma-fsrs-v6` is not adjacent to the client repository.

`SchedulerOptimizerPersistenceTest` covers migration-13 persistence, restart,
interruption recovery, cancellation, stale history, account isolation,
Discard, transactional local Apply, server-compatible history hashing, and the
existing conflict-safe profile outbox. `SchedulerOptimizerControlsUiTest`
drives the explicit candidate actions and progress/cancel surface.

## Database safety

Every schema change requires a numbered SQLDelight migration and a passing `verifySqlDelightMigration` task. Review tests must prove that a rating commits its event and immediate local projection together, that confirmed and pending history deterministically rebuilds the same projection, and that Undo deletes only the pending event before replaying all remaining history.

Tests use temporary or in-memory databases. They must never open the developer's real Kelma database.

## Manual release gate

Before a release, repeat the acceptance flow with a dedicated non-production KelmaSync account on desktop, a physical Android device, and a physical iPhone. Confirm audio routing, background/resume behavior, local-day rollover, network interruption, and process termination during study. Credentials and device access are intentionally not embedded in the automated suite.
